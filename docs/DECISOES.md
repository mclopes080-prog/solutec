# Decisões de projeto — Sprint 2

Registro das dúvidas de regra de negócio resolvidas pela opção mais simples (regra 6 do BF 02). Cada item diz **o que** foi decidido, **por quê** e **onde** está no código.

| # | Decisão | Motivo | Onde |
|---|---|---|---|
| D1 | A resposta do login segue o envelope padrão da API: `{ success, message, data: { token, usuario } }`. | Mantém o mesmo formato do cadastro e das demais rotas; o frontend trata todas as respostas igual. | `backend/src/controllers/AuthController.ts` |
| D2 | E-mail inexistente e senha errada devolvem o mesmo `401 "E-mail ou senha incorretos."`. Quando o e-mail não existe, o bcrypt ainda roda contra um hash fictício. | Não revelar quais e-mails estão cadastrados, nem pela mensagem nem pelo tempo de resposta. | `backend/src/services/AutenticarUsuarioService.ts` |
| D3 | `JWT_EXPIRES_IN` aceita segundos (`"3600"`) ou número com unidade `s/m/h/d` (`"2h"`); padrão `2h`. | Formato simples de validar no `env.ts` e convertido para segundos antes de assinar. | `backend/src/config/env.ts`, `backend/src/services/JwtTokenService.ts` |
| D4 | O `PUT /api/usuarios/me` exige `senha` + `confirmacaoSenha` toda vez (troca a senha sempre). Enviar `email` responde `400` com "O e-mail não pode ser alterado.". | A rubrica pede todos os campos obrigatórios. Para manter a senha atual, basta enviar a mesma. | `backend/src/validators/usuario.validator.ts` |
| D5 | Ids continuam sendo `cuid` (string) em todas as tabelas novas. | Mesmo padrão da tabela `usuarios` da Sprint 1. | `backend/prisma/schema.prisma` |
| D6 | O total do pedido **não é gravado** no banco: é um getter calculado a partir dos itens (preço unitário congelado × quantidade, somado em centavos). | Não há como o total ficar diferente dos itens. | `backend/src/entities/Pedido.ts` (`get total`) |
| D7 | O preço unitário é copiado do produto quando o pedido é criado ou quando os itens são editados. Depois disso, mudar o preço do produto não altera pedidos já existentes. | É o que significa "preço congelado". O cliente nunca envia preço. | `backend/src/services/PedidoService.ts` (`#montarItens`) |
| D8 | O pedido **não baixa estoque** e não confere disponibilidade. | Carrinho/checkout/pagamento estão fora do escopo; baixar estoque sem pagamento geraria inconsistência. Só se aceita produto **ativo**. | `PedidoService` |
| D9 | Transições de status: `PENDENTE → PAGO/CANCELADO`, `PAGO → ENVIADO/CANCELADO`; `ENVIADO` e `CANCELADO` são finais. Endereço e itens só podem mudar com o pedido `PENDENTE`. Só pedidos `PENDENTE` ou `CANCELADO` podem ser excluídos. | Fluxo mínimo coerente; está numa tabela única (`REGRAS_STATUS`), então mudar uma regra é editar uma linha. | `backend/src/services/pedido/transicoesStatus.ts` |
| D10 | `PUT /api/pedidos/:id` é parcial: aceita `status`, `enderecoId` e/ou `itens` (ao menos um). Os demais `PUT` (categoria, produto, endereço) são completos. | No pedido, quase toda edição é só de status; obrigar a reenviar os itens para pagar não faz sentido. | `backend/src/validators/pedido.validator.ts` |
| D11 | Excluir categoria com produtos → `409`. Excluir produto presente em pedido → `409` com a orientação "desative-o (ativo = false)". Excluir endereço usado em pedido → `409`. | Preserva o histórico; a chave estrangeira `RESTRICT` também protege no banco. | `CategoriaService`, `ProdutoService`, `EnderecoService` |
| D12 | Recurso de outro dono (endereço/pedido) responde `404`, igual a inexistente. | Não vazar a existência de dados de outros usuários. O filtro por dono vai no `WHERE` do repositório. | `EnderecoService.escopo`, `PedidoService.escopo`, `Prisma*Repository.porDono` |
| D13 | Categorias e produtos são compartilhados (não têm dono): qualquer usuário autenticado pode gerenciá-los. Não há papel de administrador. | A rubrica não pede papéis. Os CRUDs representam o painel do gestor da loja (ver `docs/PERSONA.md`). | — |
| D14 | Foi criada a rota pública somente leitura `GET /api/catalogo` (produtos ativos, paginada) para a vitrine `/produtos`. Todas as rotas de CRUD continuam autenticadas. | A vitrine precisa funcionar para visitantes sem login. | `backend/src/controllers/CatalogoController.ts` |
| D15 | `ItemPedido` é um **objeto de valor** do agregado `Pedido` (não estende `Entidade`): não tem id no domínio e é substituído por inteiro junto com o pedido. | Item não tem ciclo de vida próprio; é gravado sempre pelo repositório do pedido. | `backend/src/entities/ItemPedido.ts` |
| D16 | Listagem: `?page` padrão 1, `?limit` padrão 10 e máximo 100. Resposta `{ success, data, meta: { page, limit, total, totalPages } }`, com `totalPages` mínimo de 1. | O máximo de 100 evita consultas grandes demais e cobre os seletores do frontend. | `backend/src/validators/comum.validator.ts`, `backend/src/types/paginacao.ts` |
| D17 | `DELETE` bem-sucedido responde `204 No Content`. | Convenção REST; não há o que devolver. | `backend/src/controllers/CrudController.ts` (herdado por `CategoriaController`, `ProdutoController`, `EnderecoController`, `PedidoController`) |
| D18 | `imagemUrl` aceita um caminho relativo iniciado por `/` (ex.: `/img/produtos/camera-dome.webp`) ou uma URL `http(s)`. As imagens reais não estão em nenhum repositório; o frontend usa um placeholder SVG quando o arquivo falta. | Ver `frontend/public/img/produtos/LEIAME.md`. | `backend/src/entities/Produto.ts` |
| D19 | Usuário de demonstração do seed: `demo@solutec.test` / `Solutec@2026` (CPF fictício 111.444.777-35), com o endereço "Loja Centro". O seed é idempotente. | Precisa de um login conhecido para o teste de fumaça. O CPF é diferente do usado na coleção Bruno (529.982.247-25) para não haver conflito. | `backend/prisma/seed.ts` |
| D20 | Os arquivos seguem exatamente o **mapa obrigatório** (seção 5 do BF 02), que o guia de estudo em PDF usa. Na auditoria do BF 04 foram renomeados: `tokenService.ts` → `JwtTokenService.ts`; `PerfilUsuarioService.ts` → `ObterUsuarioService.ts` + `EditarUsuarioService.ts`; `atualizarUsuarioSchema` → `editarUsuarioSchema`; `recursos.routes.ts` → `categoria/produto/endereco/pedido.routes.ts` (+ `catalogo.routes.ts`); `pages/auth/*` → `pages/LoginPage.tsx`, `pages/CadastroPage.tsx`, `hooks/useCadastroForm.ts`; `pages/app/PainelPage.tsx` → `pages/PainelPage.tsx`; `services/session.ts` → `services/authStorage.ts`. | Arquivo com nome diferente do guia vira item "errado" na banca. | ver `docs/COBERTURA-RUBRICA.md` |
| D21 | Cada recurso tem o seu controller (`CategoriaController` etc.), mas eles **herdam** de `CrudController`, que guarda o fluxo HTTP comum. O controller concreto só informa os schemas Zod e as mensagens. As rotas usam a fábrica `criarRotasCrud` (`routes/crud.routes.ts`). | Atende ao mapa obrigatório sem repetir os 5 handlers em 4 arquivos. Também é herança legítima. | `backend/src/controllers/CrudController.ts`, `backend/src/routes/crud.routes.ts` |
| D22 | A tabela de transições de status fica em `services/pedido/transicoesStatus.ts`, como pede o mapa. `entities/StatusPedido.ts` guarda só a union `StatusPedido`. A entidade `Pedido` importa a tabela para validar `alterarStatus`. | É um módulo puro, sem dependências: a entidade continua impedindo transições inválidas por conta própria (encapsulamento), e a regra fica no caminho que o guia aponta. | `backend/src/entities/Pedido.ts`, `backend/src/services/pedido/transicoesStatus.ts` |
| D23 | Em `.claude/settings.json`, as variantes de `.env` são negadas uma a uma (`.env`, `.env.local`, `.env.development`, `.env.production`, `.env.test`…) em vez de `Read(./**/.env.*)`. | No Claude Code, uma regra `deny` vence qualquer `allow`. Então `Read(./**/.env.*)` também bloquearia o `.env.example`, que os agentes precisam ler. | `.claude/settings.json` |
| D24 | O teste de fumaça da API também roda **sem banco**: `backend/tests/http.contrato.test.ts` sobe um Express real com os mesmos controllers, rotas, middleware e `errorHandler`, trocando o Prisma por repositórios em memória. Ele confere os códigos 200/201/204/400/401/404/409/422. | A máquina onde a entrega é montada não tem MySQL. O teste com banco real (`prisma:deploy`, `prisma:seed`, Bruno) continua na máquina do dono do repositório. | `backend/tests/http.contrato.test.ts` |
